# Course-TA creation: `course-agent-creation-agent`

> Source snapshot: 2026-09-30; Unreleased; source presence is not deployed configuration.

The specification generator is the named **`course-agent-creation-agent`**,
called **CACA (Teaching Assistant Creation Agent)** in source comments.
The surrounding durable job, prompt assembly, tool registration and TA
provisioning are application code, not additional agents.

This is not a separate learner model, a fine-tuning process, or a service that
creates one lifelong agent for every learner. It creates/configures a named
course TA that learners subsequently use through the [TA harness](course-ta.md).

## Inputs and outputs

[CourseCreationRequest][schemas] accepts the course/TA name, level, duration,
context, prerequisites, textbooks, teacher-curated URLs, starters, and a material
draft session. It also carries permitted model/search configuration and course
metadata. The authenticated account supplies ownership; a conflicting creator
identity is rejected.

The specification response has two validated fields: `description` and
`instructions`. The [CACA prompt][caca] asks for course-specific identity,
representative threshold/misconception/probe examples, notation, contextual
framing, and teacher preferences. These examples are not the complete
curriculum generated by the [textbook and threshold-concept research workflow](curriculum-research.md).

Outputs are a named agent version, course setup/metadata, a creation-status
record, and related material/curriculum work. "TA created" is deliberately
separate from "materials ready" and "curriculum ready."

## Current entry points

The [course-creation router][routes] owns the durable API.

| Route | Purpose |
| --- | --- |
| `POST /api/agents/create-async` | Submit creation against an owned material draft; returns accepted job status. |
| `GET /api/agents/creation-jobs/{job_id}` | Retrieve the creation phase, material status, error, and eventual result. |
| `POST /api/agents/creation-jobs/{job_id}/retry` | Resume eligible saved creation work. |
| `POST /api/agents/{agent_name}/course-curriculum/retry` | Independently recover curriculum generation after course creation. |

The material draft and indexing lifecycle remain with the existing
[course-material routes][materials]. The persisted creation workflow is not
a separate HTTP service or remote agent.

## Sequence and ownership

1. `start_creation` in [utils/course_creation.py][creation] normalizes the
   request, binds the owner, reserves the course name, and stores an input
   digest. Repeating an unchanged request reuses saved work; changed input is
   rejected rather than silently changing an in-flight creation.
2. `advance_creation` persists phase checkpoints:
   `preparing` -> `creating` -> `saving` -> `created`.
3. Preparation generates the specification and prepares applicable memory
   configuration independently, preserving successful checkpoints if one fails.
4. `generate_specification` sends a versioned [request template][request-prompt]
   to the CACA named-agent reference. The request uses `store=False` and
   `tool_choice="none"` so tool output cannot substitute for the JSON contract.
5. A completed response must validate as `CourseSpecification`; malformed,
   incomplete, or extra-field output is rejected with a bounded retryable
   failure. Raw text is not accepted as a successful specification on this path.
6. `create_foundry_agent` unifies prompts, constructs tools, and calls
   `agents.create_version`. Saved job metadata distinguishes a version owned by
   this job from an unrelated existing agent of the same name.
7. `persist_created_course` saves setup in Blob Storage and metadata in Cosmos,
   invalidates metadata caches, and queues curriculum work when applicable.
8. `creation_status` returns the created course with its separate material
   readiness indicators. Learner chat then uses the existing named TA.

## Prompt composition and tools

[unify_agent_prompts][unifier] combines the five active core modules with the
course specification and additional context. The modules own identity/behavior,
pedagogy, tool handling, grounding, and safety. CACA supplies what varies by
course rather than replacing those shared rules.

The current durable path passes the specification as `learning_prompt` and uses
`exam_prompt=None`; the unifier still supports optional assessment notes.
Historical comments saying CACA always returns separate learning/exam prompts
are not the current `CourseSpecification` response contract.

[AgentToolBuilder][builder] attaches supported function tools and requested
hosted retrieval capabilities. Course search is scoped by the material session.
Failure to attach requested document search is not silently treated as a
search-capable TA. General web search is disabled in this creation path;
teacher-configured custom search is a separate option.

Updating local Markdown does not update an existing remote named agent.
Prompt regeneration is an explicit editor-authorized operation in
[main.py][main], separate from documentation and from creating another course.

## Related names and older paths

- `call_meta_agent_for_prompt` and older creation/regeneration helpers remain
  in `main.py`. That older parser can fall back to raw text; do not generalize
  the durable path's strict response validation to every helper.
- [BaseAgentManager][manager] is used directly by the legacy creation helper.
  Its `create_agent` checks duplicate names and forwards creation options; the
  caller passes `save_to_config=False`. It is not the durable
  reservation/checkpoint orchestration above and is not the chat harness.
- **CCA: Course Conversational Agent** names the older builder/edit
  conversation flow in `main.py`, not a learner-facing teaching runtime.
- The [Course Companion form assistant][form] validates suggested form results
  for teachers/admins. It is another configuration aid, not the CACA
  specification/provisioning job and not proof of lifelong learner-agent support.

## State, memory, and failure boundaries

Creation owns course-level setup, job state, and named-agent configuration.
It does not create verified learner mastery or crossing results.
Graph memory and its existing conditional worker are
[disabled by default][memory-settings]. Current creation/tool-building code can
omit hosted summary memory when opt-in learner memory is enabled. Consult the
[memory overview](../memory/overview.md) for scopes, modes, and operational
requirements rather than assuming every new TA gets the same memory backend.

The routes require active teacher/administrator access and draft ownership.
Reservations, input digests, and persisted checkpoints reduce duplicate work.
An uncertain remote creation is not permission to blindly create again:
`agent_create_started` and ownership metadata support confirmation on recovery.
Name conflicts, changed drafts, and active leases must be resolved through the
status/retry contract.

Completion is not a transaction across all remote services. Failed work can
leave saved checkpoints or partial resources; a successful course result can
still report pending materials. Prompt safeguards and PII redaction do not
replace authorization, data minimization, secret management, or human review.

## Verification and related guides

[Creation/generation tests][tests] exercise idempotency, name reservations,
checkpoint reuse, bounded invalid-specification failures, readiness separation,
and curriculum retries. [Tool/prompt tests][tool-tests] check core-module
deduplication and search-scope/attachment contracts. These are engineering
checks, not a live deployment or pedagogical validation.
